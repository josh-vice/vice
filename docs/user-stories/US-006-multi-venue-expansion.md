# US-006: Multi-venue trading expansion

Story schema v2. Status: Live-read verified public foundations; private and execution paths remain blocked.

As a trader who splits flow across venues, I want Vice to support additional perp DEXs (Lighter, Nado) and centralized exchanges (Blofin, then Binance) with the same identity, custody, and reconciliation guarantees as Hyperliquid, so that one terminal covers my execution without weakening safety.

## Acceptance criteria

- Venue support ships in families: perp DEXs first (Lighter, Nado — wallet/agent signatures, browser-local signing), then CEXs (Blofin, Binance — encrypted device-local API keys, never transmitted to Vice servers).
- The `dex-trait` abstraction (or its TypeScript equivalent) gains one working adapter per venue covering market catalog, book/trades/candles feeds, place/cancel/modify, fills, and account state; `DexId` gains `Blofin` and `Binance`.
- Every venue routes with that venue's exact instrument identity; display symbols are never routing keys. Cross-venue symbol collisions (e.g. BTC perp on three venues) remain distinct markets in the watchlist and account projections.
- Builder codes are attached on venues that support them; referral/affiliate codes are used on venues that do not (Blofin, Binance broker/referral programs), with the same fail-closed, explicitly disclosed, never-blocking consent model as US-002.
- Feed health, staleness, reconnection, and account reconciliation report per-venue; one venue degrading never falsely marks another venue stale.
- Order types exposed per venue are only those certified on that venue; certification flags become venue-scoped.
- A venue that is configured off is absent from production navigation (US-001 semantics).
- US-006-AC-001: Given a trader with Lighter and Hyperliquid connected, when the Hyperliquid feed degrades, then Lighter markets remain live and actionable while Hyperliquid surfaces are explicitly degraded.

- Action IDs: story.us-006

## Operational contract

- Persona: Multi-venue trader executing on Hyperliquid plus at least one additional DEX or CEX.
- Preconditions: Per-venue adapter certified; per-venue credentials (agent key or encrypted API key) unlocked; per-venue live feed and account snapshot.
- Success behavior: Orders route to the selected venue with exact venue identity, venue-native precision, and venue-appropriate builder/referral attribution.
- Failure behavior: Venue rejections map to the shared semantic categories; transport uncertainty blocks duplicate mutations per venue; a failed venue never blocks the others.
- Reconnect behavior: Per-venue generation-guarded resubscription and account reconciliation, identical in rigor to the Hyperliquid path.
- Restart behavior: Per-venue journals and persisted algo jobs restore independently; no venue replays a command without authoritative proof.
- Stale/offline behavior: Stale venues fail closed for new signing while cancellation/reconciliation remain available; unaffected venues stay live.
- Custody expectations: DEX signing stays browser-local; CEX API keys are AES-GCM encrypted at rest, device-local, account-scoped, and never sent to Vice infrastructure.
- Latency expectations: Per-venue receipt-to-store p99 <5 ms and action-to-signed-dispatch p99 <10 ms on the reference desktop, measured and gated per venue.
- Telemetry: Record venue ID, command IDs, per-venue dispatch/ack latency, rejection categories, and attribution state without credentials.
- Linked tests: venue adapter contract tests mirroring `execution/venueFormat.test.js`, `blofin/setup.test.js`, per-venue journal/reconciliation suites, catalog identity tests, and funded per-venue E2E.
- Funded-mainnet evidence: Each venue requires its own funded (or venue-testnet) place/partial-fill/modify/cancel/reconnect/restart evidence before exposure; CEX venues additionally require key-rotation and revoked-key failure evidence.

## Evidence

- Hyperliquid canonical public-event slice: accepted WebSocket L2 books and HTTP L2 baselines now pass through a canonical `EventEnvelope`; a late HTTP baseline cannot replace an accepted live frame. The envelope uses the exact catalog `InstrumentId`, connection and book-subscription epochs, venue timestamp when supplied, local receipt time, and a per-subscription ordinal. Hyperliquid does not supply a book sequence, so `venueSequence` remains absent rather than fabricated. A missing canonical identity makes the feed stale and uses the existing recovery path. Coverage: `venue/hyperliquid.test.js` and `hl/subscriptionsIdentity.test.js`. This is static/local architecture proof only.
- Lighter catalog slice: `lighter/public.ts` reads only the official `orderBookDetails` endpoint and creates a canonical `InstrumentId` only for active spot symbols that carry one exact base/quote pair and fixed decimal precision. The current perpetual response has numeric asset IDs but no settlement-asset symbol, so every perpetual stays metadata-only with no instrument, route, account, signing, or UI exposure. The venue capability declaration remains `reviewOnly`; venue documentation is not a Vice certification. Coverage: `lighter/public.test.js` and `venue/identity.test.js`. On 2026-07-29, the adapter read 209 active mainnet records: 7 canonical spots and 202 intentionally non-routable perpetual records. No credential, wallet, order, or transfer action occurred. This is live-read catalog proof only.
- Lighter public-book slice: `lighter/publicWs.ts` and `lighter/publicFeed.ts` use Lighter's documented public read-only stream only for catalog-created spot identities. The lifecycle waits for Lighter's application `connected` handshake before its exact `order_book/{marketId}` subscription, accepts the live `subscribed/order_book` snapshot only before state exists, requires every later `update/order_book` `begin_nonce` to equal the preceding `nonce`, and reconnects after a gap or invalid frame. A native transport can send documented control-frame pings; a browser transport cannot, so an idle browser socket may be venue-closed and recovered rather than claiming persistent ping support. The endpoint is pinned to Lighter's documented `readonly=true` mode; no credential, account, signing, or mutation code is present. Coverage: `lighter/publicWs.test.js` and `lighter/publicFeed.test.js`. On 2026-07-29, the implemented adapter received an ETH/USDC subscribed snapshot after the handshake (`nonce` 17979891573; 200 bid and 65 ask levels). This is one live public snapshot read plus static lifecycle proof, not browser reconnect, account, or execution evidence.
- Nado catalog slice: `nado/public.ts` reads only the official V2 archive `contracts` endpoint and keeps each accepted product as metadata-only. The response preserves exact product ID, ticker, base/quote strings, type, and mark price, but does not publish fixed price/size increments or a contract multiplier; the module therefore creates no canonical instrument, signer route, account path, or UI exposure. Nado's V2 pairs endpoint advertises additional spot pairs, but the archive contracts endpoint currently returns only priced perpetual contracts, so the adapter does not merge or infer terms across the two sources. Coverage: `nado/public.test.js` and `venue/identity.test.js`. On 2026-07-29, it read 72 priced mainnet perpetual records with no credential, wallet, order, or transfer action. This is live-read catalog proof only.
- Nado raw public-depth slice: `nado/publicWs.ts` constructs only the exact unauthenticated `book_depth` subscription and preserves the venue's x18 prices, quantities, and nanosecond timestamps as strings. An authoritative MarketLiquidity snapshot is required before any queued delta can apply; the first delta must bridge from the snapshot and every later `last_max_timestamp` must exactly continue the preceding `max_timestamp`. The module has no float conversion, canonical `InstrumentId`, signer, account, or UI route. Coverage: `nado/publicWs.test.js`. On 2026-07-29, a credential-free local Bun client could not complete the Nado public WebSocket connection, so this is static protocol proof only, not live-stream, terminal, or execution evidence.
- Hyperliquid canonical-identity slice: core perp, HIP-3, spot, cached, and bootstrap descriptors now carry the shared `InstrumentId`; outcome rows remain metadata-only because venue metadata does not supply complete execution terms. The identity preserves the exact API coin and asset/unit fields. Its price rule is explicitly five significant figures plus the venue's size-dependent decimal ceiling, rather than a fabricated fixed tick; size increment derives from `szDecimals`. Coverage: `hl/markets.test.js` and `venue/identity.test.js`. This is static/local architecture proof only.
