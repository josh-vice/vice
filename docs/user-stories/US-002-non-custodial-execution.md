# US-002: Non-custodial local execution

Story schema v2.

As a trader, I want Vice Terminal to execute through my wallet-approved Hyperliquid agent without giving Vice custody of a private key, so that I retain control while orders remain fast.

## Acceptance criteria

- Connecting a wallet establishes the authoritative account identity but does not grant trading authority.
- Enabling trading explicitly discloses local-agent behavior and any configured 0.1 bp builder fee. Builder tagging is fail-closed until `VITE_HL_ENABLE_BUILDER_REVENUE=true`; a configured builder address alone never changes order economics. Eligible signed orders disclose the fee after approval; native venue-managed TWAP is explicitly excluded because the current Hyperliquid API/SDK does not accept builder metadata for it.
- A new agent key is generated in the browser, approved by the connected main wallet, encrypted with AES-GCM, and persisted only as ciphertext scoped to that account and network.
- Unlocking requires a deterministic wallet signature and verifies that the decrypted agent address equals the stored agent address.
- Order signing occurs in the browser; Vice server routes reject place, cancel, modify, and algo execution.
- Runtime smoke explicitly verifies hosted order mutation routes return `410` and the generic hosted algorithm route remains unavailable; the only server-side HL paths are read-only projections used for status/reconciliation.
- The main account address used for snapshots must equal the wallet that unlocks or creates the agent.
- Orders, cancels, and modifications route with the registry's exact asset ID and venue precision.
- Each command receives an account/network-scoped persisted monotonic sequence; reservations are serialized with Web Locks across browser tabs (and an in-context queue fallback), order slots derive deterministic 16-byte cloids, and sequences never reuse after reload.
- Transport failures get at most one bounded retry using the same signed order payload and cloids; unresolved outcomes remain explicitly uncertain and require reconciliation rather than a new duplicate order.
- Place, Scale, Modify, Cancel, TWAP, and dead-man `scheduleCancel` commands persist a bounded account/network-scoped local journal before transmission. Pending or uncertain entries survive browser restart; Place/Scale reconcile by authoritative cloid, Cancel reconciles by authoritative order presence, Modify reconciles by the authoritative limit or trigger price, and TWAP cancellation reconciles by authoritative TWAP history. A TWAP creation with no returned venue ID remains explicitly uncertain because it cannot be safely replayed or proven from a generic order snapshot. Any uncertain outcome now blocks further place/modify/scale/TWAP mutations in the same live session as well as after restart; the client never silently retransmits a command from journal recovery.
- A live, non-private account view can explicitly download its local execution audit. The schema-v1 JSON record preserves account/network identity, command ID, sequence, cloids, exact target/venue IDs, lifecycle status, and timestamps in deterministic sequence order. It excludes encrypted agent material, private keys, signatures, raw request bodies, and raw venue error text. The download remains browser-local and performs no upload.
- Every signed mutation carries one absolute `expiresAfter` timestamp shared by the initial attempt and its bounded retry; the client never relies on a stale numeric SDK default or silently extends a command window.
- Builder metadata is attached only after builder approval succeeds. Referral assignment is never attempted during unlock; an explicit user action queries the master referral state, offers the configured code only when unassigned, verifies the resulting state, and never blocks trading.
- Account reconciliation includes an authoritative read-only referral, user-fee, and reward snapshot; the UI shows live values only when both Hyperliquid queries succeed and otherwise shows a degraded state with no local estimate.
- Account WebSocket events are reconciled through serialized, coalescing snapshots; stale responses cannot overwrite a newer wallet generation, and a wallet switch detaches the old in-flight cycle before the new account synchronizes.
- Read-only account, book, referral, fee, fill, TWAP, and open-order reads use the same typed `@nktkas/hyperliquid` InfoClient and network selection as the browser market layer; the legacy read-only SDK is not part of the production path.
- Venue rejections are mapped to semantic categories (margin, precision, post-only, reduce-only, rate limit, authorization, builder, or transport) before reaching the trader; transport outcomes remain reconcilable.
- Post-only and IOC are mutually exclusive at both the ticket and execution boundary; an invalid combination is rejected before local signing or venue transmission. `hl/orderFlags.test.js` guards this invariant.
- Builder attribution is order-type aware: native TWAP remains untagged and carries no Vice builder fee rather than receiving an invalid or misleading builder payload. `execution/revenueConfig.test.js` guards this invariant.
- Builder tagging also fails closed whenever the authoritative referral/fee snapshot becomes stale or degraded during a session; trading remains available without Vice attribution until the snapshot is live again.
- Every local mutation acknowledgement schedules a non-blocking authoritative account snapshot so fills, referral state, user fees, and builder rewards converge even when the venue WebSocket update is delayed; the reconciliation is not awaited on the signing/venue acknowledgement path.
- Account connectivity subscribes to Hyperliquid `orderUpdates`, `userFills`, `userTwapHistory`, `clearinghouseState`, and `spotState`; all events trigger the same serialized, generation-safe snapshot coordinator so balances and positions are not reconstructed from partial event payloads.
- The selected perp additionally owns an `activeAssetData` subscription that is replaced on exact-market changes and torn down when switching to spot or disconnecting; spot account state remains on `spotState`. Its events also reconcile through the same snapshot path.
- Active-asset replacement is generation-guarded, so overlapping market switches cannot restore an obsolete subscription or leak stale asset events into the current account.
- Active-asset synchronization is independently exposed in the connected navbar as `ASSET` health, so a degraded selected-perp stream is visible without falsely marking the authoritative account snapshot unavailable.
- An active-asset subscription failure schedules full private-subscription recovery rather than only refreshing a snapshot, preventing a permanently stale selected-asset stream after reconnect.
- If Hyperliquid explicitly rejects builder attribution after unlock, the client retries the same signed command without builder metadata only when no venue order ID was accepted; partial acceptance and transport uncertainty remain reconciliation-blocked and are never replayed.
- Batched venue responses with any accepted child and any rejection (including bracket and Scale) are journaled as uncertain, even when the venue returns a synchronous response; new mutations remain blocked until open-order/fill reconciliation proves the final child set.
- All execution-facing helpers consume the selected `MarketDescriptor` or its exact `marketKey`/`apiCoin`; display symbols are not used to derive asset IDs or route cancellations/modifications. Base and quote labels come from catalog metadata.
- The local signer rejects any native intent whose API coin differs from the selected descriptor before allocating a venue order or signing payload; native intents contain no display-symbol routing field.
- The local signer also requires the selected descriptor's canonical Hyperliquid instrument before every place, cancel, modify, Scale, and TWAP mutation. The canonical key, API coin, product, base/quote/settlement assets, contract multiplier, significant-figure price rule, and size increment must still match the descriptor; outcome or metadata-only rows fail closed.
- Every master-wallet mutation (agent approval, builder-fee approval, and explicit referral assignment) re-reads `eth_accounts` immediately before signing and rejects an account switch; referral assignment also rechecks after the wallet prompt before reporting success.
- Unsupported advanced algorithms remain hidden and closed until authenticated signed child-intent orchestration exists.

## Operational contract

- Persona: Wallet-connected trader placing or managing Hyperliquid orders from a browser device.
- Preconditions: Matching wallet account, unlocked encrypted local agent, live account snapshot, live selected-market feed, and no unresolved command journal entry.
- Success behavior: Browser-local signer sends exact-identity commands to Hyperliquid and returns authoritative acknowledgements or reconciled outcomes.
- Failure behavior: Deterministic venue errors reject semantically; transport uncertainty blocks duplicate mutations until reconciliation proves the outcome.
- Reconnect behavior: Re-fetch account snapshots, open orders, fills, TWAP history, referral/fee state, and reconcile the journal after generation-safe reconnect.
- Restart behavior: Unlock the account-scoped vault, restore sequence/journal state, and reconcile before allowing new mutations.
- Stale/offline behavior: Block new signing while account, market, or feed state is stale; cancellation and reconciliation remain available where safe.
- Custody expectations: Hosted routes are read-only; the master wallet approves the device-local agent, and displayed/executing accounts must match before master mutations.
- Latency expectations: Local processing p99 <2 ms and action-to-signed-dispatch p99 <10 ms on the reference desktop; venue acknowledgement is measured separately.
- Telemetry: Record command IDs, sequence/cloid, dispatch/ack/reconciliation latency, uncertainty, rejection category, and builder attribution state without private keys.
- Linked tests: `agentVault.test.js`, `commandIdentity.test.js`, `commandJournal.test.js`, `identityBoundary.test.js`, `revenueConfig.test.js`, Rust contracts, smoke, and funded-testnet E2E.
- Funded-mainnet evidence: First approval, unlock, place, partial fill, modify, cancel, rejection, reconnect, restart, and account-switch replay with venue order IDs is required before mainnet.
- US-002-AC-001: Given a matching unlocked account and live market, when a signed command loses its acknowledgement, then the same cloid is reconciled before another mutation is permitted.
